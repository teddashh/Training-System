# Original defensive microlearning. Each row becomes a separate course.
@ Git and Delivery Security | Secure development
Protected branches | A maintainer can push directly to the release branch without review or required checks. | Enforce reviewed changes and required checks, restrict bypass privileges, and audit exceptions. | Branch protection is effective only if its bypass paths are controlled. Test rules for administrators, automation identities and emergency processes; record approved exceptions and restore normal controls afterward. | Add a note asking maintainers to be careful. | Give every developer bypass access so releases are faster.
Secrets in CI | A pull-request job prints deployment credentials in a diagnostic step. | Stop exposure, revoke the credentials, and separate untrusted builds from privileged deployment jobs. | CI logs and artifacts can outlive the job. Masking helps prevent accidental display but does not make untrusted code safe to run with secrets; grant short-lived scoped credentials only where needed. | Delete the visible log but keep using the credentials. | Pass more secrets to the job so troubleshooting is easier.
Commit identity | A commit displays a familiar author name, but nobody reviewed the actual changes. | Verify the authenticated contribution path and require independent review and checks. | Author metadata alone is not proof of identity or intent. Verified signatures can help establish provenance, but even a signed commit still needs code review and authorization for the change. | Accept the commit because the displayed email matches an employee. | Treat a signature as proof the code is safe.
Secret files in repositories | A developer accidentally adds a local credentials file to a repository. | Revoke exposed credentials, remove the file through the incident process, and add preventive scanning and ignore rules. | Removing a file from the latest revision does not erase history or clones. Treat real credentials as compromised and review access before deciding how to clean repository history. | Add the file to gitignore and assume earlier commits are safe. | Rename the file and keep its contents in the repository.
Exposed Git directories | A web deployment includes the repository's .git directory under its document root. | Remove repository metadata from the served artifact and deny access while checking exposure. | Source history can reveal implementation details and old secrets. Deploy a deliberate build artifact, test forbidden paths and rotate any credentials that may have been exposed. | Hide the directory from the homepage but leave it downloadable. | Rely on visitors not guessing the path.
Leaked access tokens | A personal access token appears in an issue attachment. | Revoke the token immediately, assess use, and replace it with a minimally scoped credential if still needed. | Deleting the attachment does not invalidate copies. Review token activity and affected resources, and avoid long-lived broad tokens when a short-lived workload identity is available. | Delete the attachment and keep the token until its scheduled expiry. | Change the account display name to make the token harder to use.
Untrusted pull requests | A contributor modifies the CI script in a pull request from a fork. | Run untrusted changes without privileged secrets and require review before privileged workflows execute them. | The build script is executable code. A safe review process must consider workflow changes, dependency scripts and artifacts passed between jobs, not only the application's source files. | Run it with production secrets to match the release environment. | Trust it because the pull request changes only test configuration.
Secrets in history | A credential was removed months ago but still appears in an old commit. | Rotate the credential and investigate exposure before any coordinated history cleanup. | History rewriting does not remove copies in forks, caches or local clones. Coordinate disruptive cleanup with repository owners and use scanning to prevent recurrence. | Rewrite history and assume rotation is unnecessary. | Keep the credential because the current branch no longer contains it.
@ API Security | Secure development
Function-level authorization | A normal user can call an administrative API action even though its button is hidden. | Enforce role and action authorization on the server for every entry point. | Navigation visibility is a usability choice, not an access control. Test direct requests across roles, including alternate methods and background endpoints, with a default-deny policy. | Hide the button more thoroughly. | Check authorization only on the landing page.
Object-level authorization | Changing a record ID lets one user read another user's training record. | Scope the object lookup to the requesting user's authorized records and test cross-user access. | Knowing or guessing an identifier must not grant permission. Opaque IDs reduce guessing but do not replace ownership, organization and relationship checks for every read and write. | Replace numeric IDs with UUIDs and remove the permission check. | Verify only that the user is logged in.
Authentication boundaries | An API accepts expired tokens if the client sends a skip-check flag. | Validate token authenticity, lifetime and intended audience on the server without client-controlled bypasses. | Authentication must be consistent across endpoints. Use a supported identity implementation and reject invalid credentials predictably; test refresh, logout and recovery paths as well as ordinary login. | Trust the flag only when the client uses HTTPS. | Let the browser decide whether the token is expired.
Response minimization | A profile API returns salary and recovery fields although the interface only shows a name. | Return an explicit allowlist of fields authorized for the caller and use case. | Client-side hiding does not protect data already transmitted. Review nested serializers, exports, error messages and debug responses for unnecessary sensitive information. | Keep the fields and remove them with CSS. | Encode the response to make the hidden fields less obvious.
API inventory | An old API version remains reachable after the replacement is deployed. | Inventory versions and owners, retire unused endpoints, and apply controls to supported versions. | Forgotten endpoints often retain weak authentication or outdated dependencies. A versioned route is still part of the attack surface until access is removed and consumers have migrated. | Stop linking to the old API and assume it is retired. | Leave it unmonitored because new clients use the replacement.
Injection boundaries | An API builds a database query by concatenating a filter supplied by the caller. | Use parameterized queries and validate the permitted structure of filters. | Treat values as data and allowlist structural choices such as sort fields. Escaping by hand is error-prone, and authentication does not make caller-controlled input trustworthy. | Remove spaces from the filter before concatenating it. | Accept any filter from authenticated callers.
Security event logging | Repeated authorization failures occur, but logs contain only successful requests. | Record actionable security events with correlation IDs and appropriate access and retention controls. | Logs should help responders reconstruct events without exposing passwords, tokens or unnecessary personal data. Test alert routing and response ownership rather than collecting data nobody reviews. | Log complete credentials to make correlation easier. | Record nothing until a confirmed breach occurs.
Mass assignment | A profile update endpoint blindly copies JSON fields into a user model, including role. | Use an explicit write-field allowlist and separate privileged updates with authorization checks. | Data binding can cross a privilege boundary when model fields are exposed automatically. Test extra and nested properties, and keep server-controlled values out of ordinary client update schemas. | Hide the role field in the form only. | Trust unknown properties because the request is authenticated.
API configuration | A production API exposes detailed stack traces and an unrestricted diagnostic endpoint. | Disable unnecessary diagnostics, restrict administrative interfaces, and use reviewed production settings. | Defaults and troubleshooting settings can reveal secrets or enable unintended actions. Check configuration in the deployed environment and preserve useful internal diagnostics without exposing them to ordinary callers. | Remove the diagnostic link but keep the endpoint public. | Leave debug mode enabled to simplify support.
Resource consumption | A report endpoint accepts unlimited date ranges and concurrent requests from one account. | Bound work, paginate results, set quotas and timeouts, and monitor expensive operations. | Authentication alone does not protect shared capacity. Apply limits based on actual cost and caller context, and return clear retry behavior without allowing one request to exhaust the service. | Add more servers while leaving request cost unbounded. | Limit only unauthenticated users.
@ Web Application Security | Secure development
Clickjacking | A sensitive action can be embedded in an unrelated site's invisible frame. | Restrict framing with an appropriate frame-ancestors policy and protect sensitive actions independently. | A user can be tricked into clicking a genuine interface through another page. Allow only required framing origins and verify legitimate embedded use cases before deployment. | Hide the page title when it is framed. | Assume CSRF protection alone prevents all deceptive framing.
Command execution boundaries | A server passes a filename from a request into a shell command string. | Prefer a direct library or argument-based process API, validate inputs, and avoid invoking a shell. | Shell metacharacters can change command meaning. Run necessary processes with minimal privileges and bounded resources; quoting mistakes and string filtering are fragile defenses. | Remove one dangerous character and keep concatenating. | Trust filenames from logged-in users.
Vulnerable dependencies | A deployed component has a relevant security advisory and the team is unsure where it is used. | Identify affected versions and paths, evaluate exposure, and apply a verified update or documented mitigation. | Dependency inventories and lockfiles support repeatable assessment. Test updates and track unresolved exceptions with owners; a clean scan is a point-in-time result, not a permanent guarantee. | Ignore the advisory because the package is indirect. | Update production dependencies without checking compatibility or rollback.
Cross-site request forgery | A cookie-authenticated endpoint changes settings through a request an unrelated website can submit. | Validate anti-CSRF protections for state-changing requests and use appropriate cookie and origin controls. | Browsers may attach credentials automatically. SameSite cookies help but should match the application's actual flows; do not put state changes behind a harmless-looking GET request. | Require only that a session cookie exists. | Use GET because it is easier to call from forms.
File path boundaries | A download API joins a user-supplied path to a storage directory. | Resolve and validate the final path within the authorized storage root and enforce file permissions. | Encoded traversal, separators and symlinks can defeat naive string checks. Prefer server-selected identifiers mapped to approved files, and test that alternate encodings cannot escape the boundary. | Remove one occurrence of two dots from the input. | Check only that the submitted string starts with the folder name.
DOM-based script injection | A page writes a URL fragment into the document using raw HTML insertion. | Render untrusted text with safe DOM APIs or a reviewed sanitizer for necessary rich HTML. | Browser-only data still crosses a trust boundary. Track source to sink, avoid executable contexts and use CSP as an additional layer rather than a replacement for safe rendering. | Assume fragments are safe because they are not sent to the server. | Remove script tags but allow arbitrary event attributes.
Hidden routes | A restricted report is reachable by typing its URL even though no menu links to it. | Enforce authorization at the report endpoint for every request. | Discoverability is not permission. Test guessed paths, exported files and alternate formats, and make unauthorized responses avoid revealing sensitive object details. | Rename the route to a longer random-looking string. | Remove all visible links and keep the endpoint unrestricted.
Horizontal access controls | A user can update another employee's profile by changing an account ID. | Bind each operation to the authorized subject and verify ownership or delegated authority on the server. | Same-role users may still have different data permissions. Include cross-user negative tests for reads, writes, downloads and bulk actions instead of testing only administrator versus learner roles. | Check only that both accounts belong to the same role. | Disable editing the ID in the browser and trust the request.
Host header trust | Password-reset emails build their destination from any Host header received. | Use a configured trusted public origin and validate accepted hostnames at the edge and application. | Request headers are not a trustworthy source for security-sensitive links. Test reverse-proxy handling and forwarded headers so untrusted clients cannot influence reset or invitation destinations. | Trust the header because the request reached the server. | Accept every forwarded-host value for flexibility.
Redirect destinations | A login endpoint redirects to any URL in its next parameter. | Allow only approved same-site paths or explicitly trusted destinations after normalization. | An open redirect can make a malicious journey appear to begin on a trusted site. Check scheme-relative URLs, encoding and parser differences; avoid string-prefix checks that accept lookalike hosts. | Permit any URL containing the company name. | Trust a destination if it starts with the letters https.
Debug code in releases | A temporary endpoint can impersonate any user and remains enabled in production. | Remove the endpoint from production artifacts and verify that release configuration cannot enable it accidentally. | Debug shortcuts often bypass normal identity or authorization checks. Use controlled test environments and include deployment checks for temporary routes, sample credentials and diagnostics. | Hide the endpoint behind an undocumented path. | Keep it enabled for emergencies without access auditing.
Personal data in URLs | A page includes an employee's medical details in a query string. | Move sensitive data out of URLs and use authorized server-side references with minimized responses. | URLs can appear in browser history, logs, analytics and referrer data. HTTPS protects transit but does not prevent these copies; review retention and exposure if sensitive URLs were already used. | Keep the query string because HTTPS encrypts it in transit. | Shorten the URL with a public shortening service.
Reflected script injection | A search page echoes a query into HTML without context-aware escaping. | Use safe templates and encode the value for its actual output context. | HTML text, attributes, URLs and JavaScript have different rules. Avoid inline executable contexts and verify that malicious input is displayed as data rather than interpreted as code. | Block the word script and allow every other value. | Trust queries from a form on your own site.
Server-side request forgery | An image-fetch API accepts any URL and the server can reach internal services. | Restrict permitted schemes and destinations and enforce network egress controls with redirect and DNS handling. | The server's network access may exceed the user's. Validate resolved destinations, including private or metadata addresses, and do not assume one initial URL check protects later redirects. | Check only that the URL contains an image extension. | Allow all destinations if the caller is authenticated.
Session fixation | The application retains a session identifier supplied before login after authentication succeeds. | Rotate the session identifier on authentication and privilege changes, invalidating superseded sessions appropriately. | Authentication should establish a new trusted session boundary. Apply secure cookie settings and test login, logout and recovery behavior; a long random token still fails if an attacker can preselect it. | Keep the old identifier to preserve convenience. | Put the same identifier in a URL so it is easy to restore.
SQL query safety | A search feature concatenates user text into a SQL statement. | Bind values through parameterized queries and allowlist any dynamic identifiers or operators. | Bound parameters keep values separate from SQL syntax. Stored procedures are not automatically safe if they concatenate internally; review every construction path and use a least-privileged database account. | Escape apostrophes manually and assume every query is safe. | Rely on frontend validation to protect the database.
Stored script injection | A saved course description executes script when another user views it. | Sanitize permitted rich content or render it safely at every output location, including previews and exports. | Stored data remains untrusted. A value written by an authenticated author can later execute with a more privileged viewer's session; CSP is useful defense in depth but not a substitute for safe rendering. | Trust content because it came from the database. | Sanitize only the original entry form and ignore alternate import paths.
Tokens in URLs | A long-lived access token is appended to every report link. | Use an appropriate authenticated request mechanism and avoid placing reusable credentials in URLs. | Query strings can leak into logs, history and referrers. Where a one-time link is necessary, make it short-lived, purpose-bound and single-use as appropriate, and redact it from observability systems. | Keep reusable tokens in URLs because links are convenient. | Encode the token with Base64 and treat it as hidden.
Account enumeration | Password recovery gives noticeably different responses for existing and unknown accounts. | Use consistent external responses and bounded timing while applying abuse controls. | Attackers can combine response text, status, timing and rate limits to identify users. Preserve useful internal diagnostics without exposing account existence through recovery and invitation endpoints. | Change only the visible wording while leaving distinct status codes. | Publish the account list to remove the uncertainty.
Vertical privilege escalation | A learner can set their own administrator flag through a profile request. | Separate privileged role changes, authorize the actor on the server, and audit successful changes. | Roles and permission claims must come from trusted server-side state or validated identity assertions. Recheck authorization at execution time rather than trusting a previously rendered interface. | Hide the flag in the form but accept it in JSON. | Trust a role value stored in browser local storage.
Security randomness | Password-reset tokens are generated from timestamps and sequential account IDs. | Use a cryptographically secure random generator and enforce token expiry, purpose and one-time use. | Unpredictability is essential for bearer credentials. Ordinary random functions, counters and obscured identifiers are unsuitable; avoid logging raw tokens and store verifiers safely. | Hash the timestamp alone and assume it becomes unpredictable. | Increase the number of digits in the sequential ID.
XML external entities | A document importer parses uploaded XML with external entity resolution enabled. | Disable external entities and unnecessary DTD processing and restrict parser resource use. | XML parsers may read local or remote resources when unsafe features are enabled. Use maintained secure defaults and test the actual parser configuration, including nested or compressed input limits. | Trust XML because it is structured text. | Validate only the uploaded filename extension.
